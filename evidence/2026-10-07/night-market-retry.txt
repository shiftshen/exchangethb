## 追加：DNS 根因调查（03:20-03:35 +07）——结论是宿主级问题，不是本项目代码

### 更正一条自己的错误测量
首次 DNS 对照用了 `dns.Resolver().resolve4(host)` 的 promise 写法（该 API 只接受回调），四条解析器全部「0ms 失败」是**测试缺陷**，不是真实结论，已作废。

### 正确测量（`dns.promises.Resolver`，每台 12 次解析）
| 目标 | ok/fail | 中位 | max |
|---|---|---|---|
| Docker 内嵌 127.0.0.11 | 11/12 | 2034ms | 5005ms |
| 1.1.1.1 | 12/12 | 1034ms | 11047ms |
| **8.8.8.8** | **12/12** | **1032ms** | **2034ms** |
| 9.9.9.9 | 11/12 | 1036ms | 5004ms |
| 宿主第二个上游 47.84.83.155 | 9/12 | 2046ms | **28027ms** |

宿主 `resolvectl`：上游 = `47.84.83.155`(阿里云) + `1.1.1.1`。命中 47.84.83.155 时解析停顿 5-28 秒 → 这就是 worker/行情源 `EAI_AGAIN` 与 `source_timeout` 的来源。

### 试过并撤销的项目级修复（同样条件 A/B，一次性容器）
- A 默认（宿主解析器）：ok=11 fail=1 中位 2848ms
- B 固定 `--dns 8.8.8.8 --dns 1.1.1.1`：ok=11 fail=1 中位 2538ms
→ **无实质差异**（瓶颈在 Docker 内嵌解析器→宿主 systemd-resolved 这条链路，不在上游选择）。因此已把生产容器与仓库 compose 的 `dns:` 覆盖**全部撤销**（`HostConfig.Dns` 现为空，回到 compose.release-20261007b.yml），不留无效配置；容器名解析与 /api/health(databaseReachable=true) 已复验正常。

### 需要宿主/基座处理（属 PM/fujane 车道，未自行改宿主 DNS）
- 从宿主 systemd-resolved 上游列表移除或降权 `47.84.83.155`（或为其加超时/健康检查）；这会影响**所有**项目的容器外网解析。
- 参考证据：A/B 表、`resolvectl status`、容器内 12 次解析明细，均在本次会话命令输出中，可复现命令：
  `ssh 1panel-happy 'docker run --rm --network exchangethb_net -v /tmp/dnsbench2.js:/b.js:ro node:20-alpine node /b.js'`

剩余 unavailable 的两类原因已分别查实：
- `upbit-thailand / USDT / stale_orderbook`：Upbit TH 的 THB-USDT 盘口时间戳 **656 秒前**（同交易所 THB-BTC 仅 16 秒）→ 交易所自身数据旧，校验器按「>2 分钟」正确拒绝，站点以 fallback 标注，**不是本项目缺陷，无需放宽**。
- `orbix / BTC / source_dns_failure`：宿主 DNS 链路（见上节）导致的瞬时失败，重试未能救回第二次。
