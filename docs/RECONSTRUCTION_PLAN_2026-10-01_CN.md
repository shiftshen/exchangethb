数据源：生产 `/opt/1panel/www/sites/exchangethb.com/log/access.log`，约 81 MB，记录起于 2026 年 3 月 13 日，本次末条为 10 月 1 日。下表使用完整自然月和完整七天，日期按日志的 +0700。

| 明显机器人请求 | 10,377 | 11,835 | 3,015 |
| 200 的语言页面 GET 候选请求，排除明显机器人及常见静态文件 | 7,347 | 72,275 | 2,371 |

| 404 请求 | 27,605 | 33,869 | 9,727 |

机器人初筛按 User-Agent 的 bot、spider、crawl、scan、curl、wget、python、headless、monitor 等词识别。这是可解释的初筛，不是完整人机识别。浏览器伪装、预取、React Server Components 请求、自动化测试、共享出口均可能影响数字。因此候选页面请求不是 PV，不同 IP 不是 UV，更不是独立客户。

9 月 17 日候选请求为 45,265，9 月 20 日为 18,400，合计约占月度候选请求 88.1%。进一步对这两天语言路径的 200 请求检查，分别发现单一来源贡献超过 4.1 万与 1.5 万次，且集中在少数小时。这支持“异常自动化或测试流量”的判断，但没有证据确定具体操作者或原因。

整日排除这两天后，9 月剩余 28 天共 8,610 次候选请求，平均约 308 次/日；最近完整七天平均约 339 次/日。这只能作为普通时期的请求量参考，不能作为净化后的真实访客统计。

9 月候选请求常见路径为 `/zh/cash`、`/en/cash`、`/th/cash`、`/en`、`/zh/crypto`。这些月度排序受异常流量影响，实施前需重新计算过滤后的页面和入口分布。

9 月候选页面请求中有 11,951 次携带 `www.google.com` 来源头，但来源头可伪造，不能把它等同于 Google 自然搜索点击。7 月仓库调研记录曾报告 28 天仅 6 次 GSC 点击；这是历史报告，不是当前自然流量。

### 统计缺口

- 正式容器的 GA4 Measurement ID 为空，实际 `/en` HTML 没有 GA4 loader 或 config。
- 当前 `trackEvent` 只调用 `window.gtag`；没有 gtag 时直接返回。已有点击组件不代表数据已记录。
- 本次没有取得当前 GSC 的有效授权数据。统一入口未命中 gsc，生产项目中也未发现可用的 `.secrets` 目录；没有创建或重新授权账号。
- 因此目前无法可靠回答真实 UV、渠道转化率、推广注册量和已结算收入。
- 404 中已观察到 `xmlrpc.php` 等扫描路径。需要分开统计扫描噪声、旧 URL、正常页面缺失，不能把所有 404 都视作产品错误。

建议首先建立 14 天干净基线：真实页面浏览、比较成功、地图/官网/推广点击、回访，以及机器人/内部测试单独口径。

## 4 产品定位和用户路径

建议定位：帮助旅行者、在泰居民和数字资产用户比较兑换泰铢的实际结果。首屏让用户选择“现金换汇”或“数字资产买卖”，输入金额后直接看到可解释的结果。

现金与加密货币分成两条独立路径。现金用户不应在首屏被引导购买数字资产；推广排序不能改变汇率或净到手排序。

### 首页

- 首屏只保留方向、币种/资产、金额、位置和比较按钮，默认示例不冒充用户实时结果。
- 提交后显示前三条结果、净到手、费用、数据时间、来源与下一步操作。
- 次级入口为平台详情、附近门店、经过核验的活动与方法说明。
- 采用浅色金融工具风格，大号结果数字、清晰状态标签；移动端优先，避免等层级卡片堆积。

### 现金比较

- 区分外币换 THB 与 THB 换外币，支持钞票面额差异。
- 真实门店坐标、营业时间、曼谷时区、地图导航及位置权限拒绝后的手动选区。
- 默认按兑换所得排序，另提供距离、营业状态筛选。若估算交通费，必须单独展示假设，不能把直线距离当路线成本。
- 显示分店适用范围、最后观测时间和来源。总部参考汇率不能暗示所有门店同价。
- 核实地址精度；源码中的参考坐标和长期固定 isOpen 不应直接充当实际门店定位与营业状态。

### 数字资产比较

- 区分用户已持有资产、需要链上转入与平台内买卖，买和卖分别计算。
- 依据真实可用交易对、订单簿深度、成交率、滑点、交易费和 THB 提现费比较。
- 网络费按具体链与转账阶段处理，避免把平台提币费误算成充值费或重复扣除。
- 交易对不支持、报价过期、深度不足、接口失败时明确状态，不给出虚假的最优排名。
- 首版限于已有四家平台中经过市场可用性复核的交易对，不预设每家都有 USDT/THB。

### 推广活动页

- 分别展示推荐人奖励、新用户奖励、现金/手续费券/实物类型、条件、有效期、配额与最后核验时间。
- 用户能够看见推广关系说明和官方条款。
- 按用户条件筛选活动；不把“最高奖励”表现成必得奖励。
- 暂停、过期、未核实的计划保留历史说明，停止展示“立即领奖”。

## 5 数据和工程重构

复用现有 Next.js、PostgreSQL、采集 worker、后台和 web/canary 发布体系。先组织现有模块与补齐缺口，不另起同名系统。

| 模块 | 要做的改造 | 验收证据 |
|---|---|---|
| 兑换计算 | 统一方向、单位、舍入和费用阶段；支持部分成交与最低额度 | 用公开样本订单簿和手工计算对照，覆盖买卖、费率、深度不足和币种单位 |
| 数据适配 | 每平台独立适配，超时、限流、重试和熔断；现金/加密使用不同刷新策略 | 接口失败演练不导致页面失败，标记正确且恢复可观察 |
| 数据状态 | live、cached、stale、unavailable、demo 分开；保存来源时间与抓取时间 | 过期或 demo 数据不进入默认实时最优排序 |
| 费用规则 | 费率、网络、币种、会员条件、适用日期、官方来源版本化 | 每个结果能解释费用来源和计算路径 |
| 推广计划 | 改造仅有三种 AffiliateStatus 的模型；引入 active、paused、expired、pending、official_only 及奖励和资格字段 | 过期自动降级，未核验不会显示有效奖励 |
| 出站记录 | 使用允许名单的 `/go/{provider}` 跳转，记录匿名事件后跳到已审核链接 | 不能开放重定向，参数保留规则可测，点击去重且不影响用户跳转 |
| 后台 | 数据新鲜度、采集失败、费用、活动、链接和结算集中管理，保留审计与恢复 | 每次变更可回读并可追溯，活动来源清晰 |
| 持久化 | PostgreSQL 作业务主本，明确 file_fallback 的读写与恢复策略 | 数据库短暂不可用不会形成无法发现的双份配置冲突 |
| 发布 | 构建记录源码 SHA、镜像 digest 和版本接口，区分前端与 worker 发布 | 运行版本可核验，灰度晋级同一镜像，前端回滚不删除数据库 |

当前 `resolveAffiliateLink` 的窗口判断对仅有 startAt 或仅有 endAt 的情况可能错误降级：边界使用 Infinity，却要求两端都有限。实施时加一侧边界测试并修复；本次只发现，未修改。

源码含 2026 年 3 月静态价格、费率和评分。它们不能自动视为现网正在使用，但重构必须核查所有 fallback 路径及后台覆盖，移除无方法支撑的主观评分。现有实时适配功能值得保留，本次 USDT 比较 API 样本返回 Binance TH 与 Orbix 为 live；单次返回不能证明长期准确性。

## 6 流量和收益衡量

接入真实 GA4 或一个明确选定的统计系统，并恢复既有 GSC 授权；不同时堆叠多套统计。事件至少包括 comparison_started、comparison_success、comparison_failed、result_expanded、map_click、official_click、affiliate_click。

事件维度：语言、入口、设备、币种/资产、金额区间、平台、结果排名、数据状态、活动 ID 与链接版本。避免采集精确位置和不必要的个人身份，明示隐私与保存期限。

独立展示三个漏斗：现金比较到地图/官网；数字资产比较到官网/推广；推广点击到平台确认资格及结算。本站点击只能证明出站，不能证明开户、KYC 或交易。优先使用平台官方允许的报表或回传；没有回传时用按期结算报表对账，不编造注册转化率。

商业优先级建议：

1. 核实用户 Orbix 资格和推荐码后接入，观察实际结算。
2. Binance TH 原码保留待用；普通计划恢复或特殊 Affiliate 活动获确认后再启用相应奖励。
3. Bitkub 当前活动可提供用户信息价值，但不是可重复现金收入模型。
4. 换汇商后续可协商标明赞助的展示位或线索合作。未取得协议前收入按未知处理，不联系商家或伪称合作。

Orbix 预测只允许基于确认条件计算：`50 × 合格 KYC 推荐数 + 150 × 合格首笔 token 交易数`，扣除取消与实际税务影响后对照官方结算；不能用页面浏览或普通 BTC/USDT 交易直接替代合格事件。

## 7 SEO 和内容迁移

- 先拿到当前 GSC 页面/查询数据与有效 URL 清单，复核 7 月保留、合并和重定向方案；不机械执行旧 29 条目标。
- 首版优先首页、现金工具、数字资产工具、有独特数据的商家/平台页和必要法律页。
- 保留已有中文、英语、泰语路径；按内容质量与搜索表现决定索引，不能一刀切删除语言。
- canonical、hreflang、sitemap、robots 和页面实际状态使用同一规则。参数页和旧路线页按真实替代关系单跳迁移。
- sitemap 只放可索引且有价值的页面，规模由内容和数据决定，不以数量作为验收目标。
- 商家页提供真实地址、营业、面额、汇率适用范围和来源；活动页提供核验时间和状态，避免模板薄页。
- 先改善 Ratchada、SIA 和核心工具，再依据当前 GSC 扩展币种/区域页面，停止无数据支撑的批量扩页。
- 商业链接标记 sponsored，赞助与自然比较结果分开。Binance TH 的推广限制也应进入活动审核字段，例如禁止的付费搜索投放，不把国际 Binance 规则套用到 TH。

## 8 实施顺序及预计周期

建议首版 4 至 6 周；这是工作量估计，取决于版本差异、账号接入和数据质量。各阶段产物独立可评审，不以“大重写”阻塞所有交付。

| 阶段 | 预计工作 | 产物与完成条件 |

| P0 版本与测量 | 2 至 3 工作日 | 保存服务器差异、数据和镜像；比较 GitHub 与运行镜像；确定主分支；统计事件现场验收；恢复当前 GSC 数据或明确授权缺口 |

## 9 发布验收和回退

上线硬条件：

- 源码版本与正式镜像可追溯，保留服务器原有差异，没有覆盖未审查改动。
- 计算测试覆盖买卖方向、链与费用阶段、部分成交、过期数据及不支持市场；有手工样本交叉核验。
- 360/390/768/1440 宽度无溢出，键盘和触屏可操作；定位拒绝仍可比较。
- 活动条款逐项有官方来源、状态和日期；链接经过允许名单与归属核验；已暂停链接不展示有效奖励。
- 比较成功、地图/官网/推广点击在真实统计后台可以看见，并区分内部测试。
- 无 canonical、noindex 与 sitemap 冲突；历史 URL 映射经抽样核验，不形成重定向环。
- 数据库、文件备份及镜像可恢复；正式切换复用已验收的灰度镜像，数据库与 worker 不随前端盲目重建。
- 核心页默认缓存视图可快速显示，刷新结果有状态和超时边界；移动端 LCP ≤2.5 秒、INP ≤200ms、CLS ≤0.1 为优化目标，需足够真实用户样本再判断。

上线后先观察 14 天，目标是拿到可信分母，再设转化提升指标。自然流量、点击率与推广收入不作为本次计划已经达到的结果。

回退触发：核心比较不可用、净到手计算错误、过期数据伪装实时、外跳到错误域名、持续 5xx 或迁移导致核心页面不可访问。先禁用有问题的活动/数据源；如是发布问题，回退前端镜像和相关路由配置。数据库采用兼容性迁移和单独恢复方案，不能靠恢复旧前端删除新业务数据。
